# Template parts, and what this library does with each

A WinUI control template is a list of named parts and a state machine over them. This file
says, for every part and every state of every template it covers, which element or which
condition of ours plays it — or why none does.

**It exists because six parts were found one at a time.** Over two days `SplitView`'s template
gave up a border, a corner radius, `HCPaneBorder`, `LightDismissLayer`, a clip, and a column
whose second state was unaccounted for. Each was found by someone reporting what the control
looked like on a phone, or by the next unit tripping over it. Every one of them had been sitting
in a file this repository already had, at a pin it already knew, for as long as the control had
existed. The comparison was always cheap; what was missing was anything that said it had not
been done.

So the comparison is written down, and a gate reads it. `data/winui-template-parts.json` is the
census, extracted from the pin by `scripts/parts/extract.mjs`. This file is the disposition.
**C11** joins the two and fails on a part or a state with no row, a row naming neither, a
template claimed by a component that does not exist, a reproduction that says nothing about its
states, and a `reproduced` row whose selector that component does not carry. The last of those is
the one that matters: without it these tables could be filled in one sitting without opening a
single component, and they would look exactly the same.

## A template can be reproduced more than once

`SplitView` appears twice below. `SplitView.svelte` reproduces it because it is that control;
`NavigationView.svelte` reproduces it because `NavigationView.xaml` hosts a `SplitView` and this
library renders its own pane instead of composing ours. Two reproductions, two dispositions, and
the difference between the columns is the whole of why this file was needed — every one of the
six parts was present in one column and absent from the other.

A section heading is therefore a template **and** a component, not a template alone.

## Dispositions

- **reproduced** — an element of ours plays the part, or a condition of ours is the state. The
  _Where_ cell names it and C11 requires it in the component's source: a selector, or — where the
  part is played by a rule rather than by an element — a backticked span of CSS that component
  contains. One or the other, and a cell claiming neither is refused. Where the mechanism differs
  from the template's, the cell says so: matching the template's _effect_ is the bar, not its
  markup.
- **declined** — the part or the state serves a surface this library does not offer. The cell
  names the prop that would fill it, so that adding that prop arrives with a checklist rather
  than a blank page.
- **open** — the surface is one we do offer and what we render is not what the template
  specifies. A defect, and the cell carries the two numbers or the two behaviours, so that fixing
  it needs no second reading of the pin. There is no register to point at: `docs/divergences.md`
  holds divergences that were _accepted_, and C5 requires every entry there to be cited from a
  code comment. C11 prints the count of `open` rows on every run instead, and that count is where
  a defect recorded here is tracked.
- **inert** — states only. The template declares the state and nothing in the pin enters it, so
  there is no surface to offer or decline and nothing to reproduce. The cell records the search
  that found no caller, because that is the claim; and a later pin that wires the state up makes
  the row wrong, which `declined` would not.

## Scope

The census covers both files in full — 7 templates, 80 parts, 67 states. This file disposes of
the parts of the two templates the six defects came from, over three reproductions, and the
states of one of those three. The rest are listed under _Pending_ and _Pending states_ and
counted by C11 on every run, so that what is undone is a number in the output rather than an
absence nobody reads.

**The two axes are two tables.** A `VisualState` is a different question from a part — this
control answers a state with a condition rather than with an element — so each reproduction below
has a `### Parts` table and a `### States` table, and C11 reads them separately. A reproduction
may defer its states, but only by name, under _Pending states_; deferring them silently is what
the gate refuses.

## A state is not a rule

A `VisualStateGroup` is an exclusive axis. One of its states holds at a time, entering one leaves
the last, and what a state set is undone when it is left. A CSS rule is none of that: it applies
while its selector matches, and there is nothing to leave. So a group becomes an attribute on
`.root` whose values are the states, and the setters become rules keyed on those values — and
three things follow that every `reproduced` row below is a claim about.

**The polarity can invert.** A state that sets nothing is the one the template's declared values
were written for, and its sibling is what moves away from them. `PaneOverlaying` is empty and
`PaneNotOverlaying` sets `ShadowCaster.Opacity` to 0, so upstream's caster is opaque by default
and a state hides it. Here the default is the stylesheet's, so the caster is transparent and
`[data-overlay='true']` is what shows it. Same two renderings, opposite rule.

**Exclusivity is not carried across.** `DisplayModeGroup` cannot be in two states at once;
`data-display-mode` and `data-pane-display-mode` are two attributes and nothing stops a
combination the group has no member for.

**One condition can answer two groups.** `PaneStateGroup` and `PaneStateListSizeGroup` are
separate axes upstream and are both entered from `m_isClosedCompact`, so one attribute is both
here — which is right until a pin moves one of them and not the other.

**Two dead ends, and the census is what found them.** `TitleBarVisibilityGroup` is a group of two
states that no `GoToState` in the control names, so the margin `TitleBarCollapsed` sets cannot be
reached at this pin — that is the `inert` disposition. Its mirror is `SettingsVisible` /
`SettingsCollapsed`, which `UpdateVisualState` enters on every pass (`NavigationView.cpp:3554`)
and which this template has no group for. Only the first gets rows below: the census is the
template's own names, and the template does not have the second.

**Transitions are not in the census at all.** A `VisualTransition` is identified by the pair of
states it runs between rather than by a name, so it needs a different key; `4cba9b2` records what
is known about them in the meantime.
